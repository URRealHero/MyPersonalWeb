1 GPU & Triton Basics

1.1 GPU

Modern GPUs are throughput machines. You get speed by keeping thousands of lightweight threads busy and by streaming data through fast on-chip memory.

  • SMs (Streaming Multiprocessors): independent compute units that schedule warps and run your kernel.
  • Warps: groups of (typically) 32 threads executing the same instruction (SIMT). If threads branch, the warp serializes.
  • Memory hierarchy (fastest → slowest):
    • Registers (per-thread, tiny, fastest)
    • Shared memory / on-chip SRAM (per-block/program, fast)
    • L1/L2 caches (hardware-managed)
    • Global memory (HBM) (large, high latency; high bandwidth if accesses are coalesced)
  • Performance levers:
    • Tiling: load a small tile from global → compute heavily in registers/SRAM → write back.
    • Coalescing: threads in a warp should touch contiguous addresses.
    • Occupancy: keep enough warps resident to hide latency.
    • Arithmetic intensity: do more math per byte moved.

Think in tiles, not elements. A good kernel is “load tile → compute a lot → store tile”.

1.2 Why Triton helps (vs. hand CUDA or naïve PyTorch)

Triton is a Python DSL that compiles to optimized GPU code. You write kernels at the tile level with NumPy-like vector ops; the compiler handles vectorization, coalescing, and register allocation.

What Triton buys you:

  • Block-level programming: one @triton.jit program operates on a tile (e.g., BLOCK_M × BLOCK_N).
  • Simple indexing: tl.program_id, tl.arange make 2D grids and tile addressing natural.
  • Safe 2D tiles: tl.make_block_ptr(..., boundary_check=..., padding_option=...) handles tails cleanly.
  • Mixed precision done right: compute in fp32 (out_dtype=tl.float32), store in bf16/fp16.
  • Autotuning: @triton.autotune can pick tile sizes/warps/stages per shape.
  • Portability: write Python; Triton emits CUDA kernels.

You still think like a GPU engineer (tiling, coalescing, occupancy), but without the boilerplate.

1.3 Triton kernel anatomy (must-know primitives)

  • @triton.jit: compile a Python function into a GPU kernel.
  • tl.program_id(dim): which program (a.k.a. block) am I along dimension dim?
  • tl.arange(start, size): vector of indices inside a tile.
  • tl.load / tl.store(ptrs, mask=..., other=...): vectorized memory I/O, with masks for tail tiles.
  • tl.make_block_ptr(base, shape, strides, offsets, block_shape, order): 2D tile view with strides.
  • tl.dot(A, B, out_dtype=tl.float32): matmul along the last dimension; accumulates in fp32.
  • tl.max / tl.sum / tl.exp / tl.log: warp-friendly reductions and elementwise math.
  • tl.constexpr: compile-time constants (tile sizes, head dims, etc.) for better codegen.

1.4 Minimal Triton kernel template (tile-wise map/reduce)

This is a skeleton you can reuse (layernorm, row-softmax, per-row transforms…). It shows:

  • how to build a 1D grid,
  • load a [BLOCK_M, D] tile,
  • compute in fp32,
  • store with masks.
import triton
import triton.language as tl
import torch

@triton.jit
def kernel_template(
    X_ptr, Y_ptr,               # base pointers
    stride_xm, stride_xd,       # X strides (elements, not bytes)
    stride_ym, stride_yd,       # Y strides (elements)
    M, D,                       # problem sizes: rows (M) and cols (D)
    BLOCK_M: tl.constexpr,      # compile-time tile height
    BLOCK_D: tl.constexpr,      # compile-time tile width (often equals D)
):
    # Each program processes one row tile [BLOCK_M, D]
    pid_m = tl.program_id(0)                         # which tile along rows
    row_start = pid_m * BLOCK_M
    m_idxs = row_start + tl.arange(0, BLOCK_M)       # [BLOCK_M] row indices
    d_idxs = tl.arange(0, BLOCK_D)                   # [BLOCK_D] col indices

    # Tail masks (handle last partial tile safely)
    m_mask = m_idxs < M
    d_mask = d_idxs < D
    mask2d = m_mask[:, None] & d_mask[None, :]

    # 2D pointer grids for a [BLOCK_M, D] tile
    # A[:None] is broadcasting 1D to entire 2D row
    x_ptrs = X_ptr + m_idxs[:, None] * stride_xm + d_idxs[None, :] * stride_xd
    y_ptrs = Y_ptr + m_idxs[:, None] * stride_ym + d_idxs[None, :] * stride_yd

    # Load tile → upcast for numerics (compute path in fp32)
    x = tl.load(x_ptrs, mask=mask2d, other=0).to(tl.float32)   # [BLOCK_M, BLOCK_D] ~ [BM, D]

    # ---- Your compute here (map/reduce) ----
    # Example: per-row mean-centering
    row_mean = tl.sum(x, axis=1) / D                           # [BM]
    y = x - row_mean[:, None]                                   # broadcast subtract

    # Store back (cast if needed)
    tl.store(y_ptrs, y.to(tl.float32), mask=mask2d)

def launch_template(x: torch.Tensor) -> torch.Tensor:
    assert x.is_cuda
    M, D = x.shape
    y = torch.empty_like(x, dtype=torch.float32)

    # Simple heuristics; autotune later
    BLOCK_M, BLOCK_D = 128, min(128, 1 << (D - 1).bit_length())  # power-of-two-ish
    grid = (triton.cdiv(M, BLOCK_M),)                            # 1D grid over rows

    kernel_template[grid](          # only pass grid size
        x, y,
        x.stride(0), x.stride(1),
        y.stride(0), y.stride(1),
        M, D,
        BLOCK_M=BLOCK_M, BLOCK_D=BLOCK_D,
    )
    return y

2 FlashAttention — Forward Pass (Code Walkthrough)

Below I unpack your forward kernel module by module and explain how each piece maps to the FlashAttention idea (tiling → matmul → online softmax → causal mask → finalize), and why it accelerates compared to naïve attention.

Setup: tensors are single-head with shape [B, S, D]. Heads can be folded into B later.

2.1 Launch geometry & meta-parameters

  • Grid: grid = (ceil_div(S, Q_TILE_SIZE), B) Each Triton program (“block”) processes one Q tile of Q_TILE_SIZE rows for one batch.
  • Scale: scale = 1 / sqrt(D) (scaled dot-product).

Why it’s fast Parallelizes across (query tiles × batches) for high occupancy; keeps per-program working set small enough to stay in registers/L1.

2.2 Block pointers (Q / O / L)

These build safe 2D views over tiles with correct strides and tail handling:

Q_block = tl.make_block_ptr(
    base=Q_ptr + b * stride_qb,
    shape=(N_QUERIES, D),
    strides=(stride_qq, stride_qd),
    offsets=(qtile * Q_TILE_SIZE, 0),
    block_shape=(Q_TILE_SIZE, D),
    order=(1, 0),  # D contiguous for coalesced IO
)
O_block = tl.make_block_ptr(... same tiling as Q ...)
L_block = tl.make_block_ptr(... 1D tile of size Q_TILE_SIZE ...)

Why it’s fast order=(1, 0) makes the D dimension contiguous → coalesced loads/stores along D; fewer transactions to HBM.

2.3 On-chip state (compute path = fp32)

Q_tile = tl.load(Q_block, ...).to(tl.float32)   # [bq, D]
O_acc  = tl.zeros((Q_TILE_SIZE, D), tl.float32) # numerator accumulator
m      = tl.full((Q_TILE_SIZE,), -inf, tl.float32)  # running max per row
l      = tl.zeros((Q_TILE_SIZE,), tl.float32)       # running partition sum
  • Load Q once and keep it on-chip; stream K/V tiles.
  • Keep all reductions/matmul in fp32 for stability.

Why it’s fast Reuses Q from registers; avoids reloading. fp32 accumulation avoids numerical blow-ups that would otherwise force extra passes.

2.4 Loop over K/V tiles (single pass)

k0 = 0
while k0 < N_KEYS:
    K_block = tl.make_block_ptr(... offsets=(k0, 0), block_shape=(K_TILE_SIZE, D))
    V_block = tl.make_block_ptr(... offsets=(k0, 0), block_shape=(K_TILE_SIZE, D))

    K_tile = tl.load(K_block, ...).to(tl.float32)  # [bk, D]
    V_tile = tl.load(V_block, ...)                 # [bk, D] (storage dtype)

    S_ij = tl.dot(Q_tile, tl.trans(K_tile), out_dtype=tl.float32) * scale  # [bq, bk]
    ...
    k0 += K_TILE_SIZE
  • Compute a local score tile S_ij for (Q_tile × K_tile); consume immediately.
  • No global write/read of S.

Why it’s fast Naïve attention materializes S = QK^T (O(S²) memory traffic). This keeps S_ij ephemeral (registers/L1 only).

2.5 Tail masking & causal masking (before reductions)

# Tail keys (last K-tile)
k_abs  = k0 + tl.arange(0, K_TILE_SIZE)          # [bk]
k_mask = k_abs < N_KEYS
S_ij   = tl.where(k_mask[None, :], S_ij, -1e6)   # kill OOB columns

# Causal: forbid future keys
if is_causal:
    q_abs    = (qtile * Q_TILE_SIZE) + tl.arange(0, Q_TILE_SIZE)  # [bq]
    mask_tri = k_abs[None, :] > q_abs[:, None]                    # [bq, bk]
    S_ij     = tl.where(mask_tri, -1e6, S_ij)
  • Mask early so invalid lanes can’t become the row max.
  • Use a large negative (e.g., -1e6) instead of -inf to avoid NaNs on some GPUs.

Why it’s fast Prevents bogus maxima and wasted compute; keeps the numerics well-conditioned for the next reductions.

2.6 Online softmax update (per row, streaming tiles)

We maintain row-wise (m, l) and an unnormalized accumulator O_acc. For each tile:

$$ \begin{aligned} t &= \max_{k \in \text{tile}} S_{ik} \\ m_{\text{new}} &= \max(m,\, t) \\ \tilde{P}_{ik} &= \exp(S_{ik} - m_{\text{new}}) \\ \alpha &= \exp(m - m_{\text{new}}) \\ l &\leftarrow \alpha \, l + \sum_{k} \tilde{P}_{ik} \\ O_{\text{acc}} &\leftarrow \alpha \, O_{\text{acc}} + \tilde{P} \; @ \; V_{\text{tile}} \end{aligned} $$

Code:

tmax  = tl.max(S_ij, axis=1)                  # [bq]
m_new = tl.maximum(m, tmax)                   # [bq]
P_tld = tl.exp(S_ij - m_new[:, None])         # [bq, bk]
alpha = tl.exp(m - m_new)                     # [bq]

O_acc = alpha[:, None] * O_acc + tl.dot(P_tld, V_tile.to(tl.float32), out_dtype=tl.float32)
l     = alpha * l + tl.sum(P_tld, axis=1)
m     = m_new
  • P_tld are tile-local unnormalized probabilities.
  • alpha rescales prior state when the running max increases.

Why it’s fast This computes exact softmax without ever holding an entire row of S. Memory stays O(bq·D); K/V each stream once.

2.7 Finalize & write back

$$ O = \frac{O_{\text{acc}}}{l[:, \text{None}]}, \qquad L = m + \log(l) $$
O_out = O_acc / l[:, None]
tl.store(O_block, O_out.to(O_block.type.element_ty), boundary_check=(0, 1))

L_row = m + tl.log(l + 1e-20)
tl.store(L_block, L_row, boundary_check=(0,))
  • O is the final output; cast back to storage dtype on store if needed.
  • L is rowwise log-sum-exp, saved for recomputation-based backward.

Why it’s fast We still avoid O(S²) tensors in forward; L lets backward reconstruct probabilities tile-by-tile (still streaming).

2.8 Wrapper & tests

  • The autograd.Function.forward launches the kernel with:

    • pointers + element strides (tensor.stride() is already in elements)
    • sizes (S, S, scale)
    • meta: D, Q_TILE_SIZE, K_TILE_SIZE, is_causal

  • Reference check: builds S_full in fp32, applies the same causal mask, softmax in fp32, and compares O (bf16 tolerances like atol ~ 1e-3–2e-3, rtol ~ 1e-2 are typical).

Why it’s fast All PyTorch reference ops materialize S and (implicitly) P; your Triton kernel never does. The difference grows with sequence length.

2.9 Where the speedups come from (compared to naïve attention)

Naïve pipeline

  1. S = Q @ K^T → write S (O(S²))
  2. P = softmax(S) → read S, write P (O(S²))
  3. O = P @ V → read P (O(S²))

FlashAttention pipeline

  • Never materializes S or P.
  • Streams K/V once per Q-tile; updates on-chip (m, l, O_acc).
  • Writes only O (and L) → memory traffic scales like O(B·S·D).

Less memory, fewer global reads/writes, better cache reuse → large speedups, especially for long sequences.

2.10 Practical knobs (for later)

  • Start with Q_TILE=128, K_TILE=128; add @triton.autotune over a small grid:

    • (Q_TILE, K_TILE) ∈ {(64,128), (128,128), (128,256), (256,128)}
    • num_warps ∈ {4, 8}, num_stages = 2

  • Keep fp32 accumulation: tl.dot(..., out_dtype=tl.float32).

  • Always mask tail + causal before reductions/exp.

  • Use a large negative (e.g., -1e6) instead of -inf inside kernels.

2.11 One-screen summary

Q_tile [bq,D] ───┐
                  ├─ for k0 in range(0, S, K_TILE):
K_tile [bk,D] ────┤     S_ij = Q_tile @ K_tile^T
V_tile [bk,D] ────┤     mask_tail / mask_causal
                  ├─►   m,l,O_acc ← online softmax updates
                  │
                  └─ finalize: O = O_acc / l ;  save L = m + log(l)

That’s the forward story: fix a Q tile, stream K/V once, online softmax, normalize, store O/L.

3 FlashAttention — Backward Pass (recompute, two-pass)

Backward is where FlashAttention shines: we get exact gradients without ever materializing the $S\times S$ softmax matrix. The trick is to recompute local softmax probabilities from the saved row log-sum-exp $L$ and stream over $K/V$ tiles twice.

3.1 What we saved in forward

Per query row $i$ we stored

$$ L_i \;=\; \log \sum_{j=1}^S e^{S_{ij}} \;=\; m_i + \log \ell_i, $$

so we can always reconstruct probabilities by

$$ P_{ij} \;=\; \frac{e^{S_{ij}}}{\sum_k e^{S_{ik}}} \;=\; e^{\,S_{ij} - L_i}. $$

No need to store $m,\ell$ separately—$L$ is enough.

3.2 Gradients you would compute naively

Let $O = P V$, with $S = \text{scale}\cdot Q K^\top$, $\text{scale}=1/\sqrt{D}$, and upstream gradient $\mathrm{d}O$.

  1. Softmax Jacobian (rowwise). If $y=\mathrm{softmax}(x)$ and $g=\partial \mathcal{L}/\partial y$, then
$$ \frac{\partial \mathcal{L}}{\partial x} = \big(\mathrm{diag}(y) - y\,y^\top\big)\, g = y \odot \big(g - (y^\top g)\,\mathbf{1}\big). $$
  1. Chain rule for attention:
$$ \begin{aligned} \mathrm{d}V &= P^\top\, \mathrm{d}O,\\ \mathrm{d}P &= \mathrm{d}O\, V^\top,\\ \mathrm{d}S &= P \odot \Big(\mathrm{d}P \;-\; \big(\,(P \odot \mathrm{d}P)\,\mathbf{1}\,\big)\Big), \end{aligned} $$

where the subtraction uses the rowwise scalar

$$ \Delta_i \;=\; \sum_{j} P_{ij}\,\mathrm{d}P_{ij}. $$

Finally, because $S=\text{scale}\cdot QK^\top$,

$$ \mathrm{d}Q = \text{scale}\cdot \mathrm{d}S\,K,\qquad \mathrm{d}K = \text{scale}\cdot \mathrm{d}S^\top\,Q. $$

Key observation: the only “global across keys” quantity you need per row is the scalar $\Delta_i$. That’s why we can stream.

3.3 Two-pass streaming algorithm (per Q-tile)

Inputs: $Q,K,V,\mathrm{d}O,L$, flags (causal), strides. Outputs: $\mathrm{d}Q,\mathrm{d}K,\mathrm{d}V$.

  • Fix one Q-tile $[b_q, D]$ (same tiling as forward).

  • Pass 1 (compute $\mathrm{d}V$ and $\Delta$) For each $K/V$ tile $[b_k, D]$:

    1. Recompute scores $S_{ij} = \text{scale}\cdot Q_{\text{tile}} K_{\text{tile}}^\top$.

    2. Apply tail and causal masks (same logic as forward).

    3. Recompute probabilities $P_{\text{tile}} = \exp(S_{ij} - L_i)$.

    4. Compute $\mathrm{d}P_{\text{tile}} = \mathrm{d}O_{\text{tile}}\, V_{\text{tile}}^\top$.

    5. Accumulate:

      $$ \mathrm{d}V_{\text{tile}} \;{+}{=}\; P_{\text{tile}}^\top \,\mathrm{d}O_{\text{tile}},\qquad \Delta \;{+}{=}\; \sum_{j\in \text{tile}} P_{ij}\,\mathrm{d}P_{ij}. $$

    (Apply masks to $P$ and $\mathrm{d}P$ so masked entries contribute 0.)

  • Pass 2 (compute $\mathrm{d}Q$ and $\mathrm{d}K$) Re-loop over the same tiles:

    1. Recompute $S_{ij}$ and $P_{\text{tile}}$ as above.

    2. Recompute $\mathrm{d}P_{\text{tile}} = \mathrm{d}O_{\text{tile}}\, V_{\text{tile}}^\top$.

    3. Form $\mathrm{d}S_{\text{tile}} = P_{\text{tile}} \odot \big(\mathrm{d}P_{\text{tile}} - \Delta[:,\text{None}]\big)$.

    4. Accumulate:

      $$ \mathrm{d}Q_{\text{tile}} \;{+}{=}\; \text{scale}\cdot \mathrm{d}S_{\text{tile}}\, K_{\text{tile}},\quad \mathrm{d}K_{\text{tile}} \;{+}{=}\; \text{scale}\cdot \mathrm{d}S_{\text{tile}}^\top\, Q_{\text{tile}}. $$

  • Write back $\mathrm{d}Q_{\text{tile}}$. For $\mathrm{d}K,\mathrm{d}V$ (shared across Q-tiles), use either atomic adds or partition work to avoid write conflicts.

Why two passes? Because $\Delta_i$ needs a sum over all keys. We first collect $\Delta$ and $\mathrm{d}V$ while streaming once, then use $\Delta$ to form $\mathrm{d}S$ in a second stream.

3.4 Masking & stability details

  • Tail mask (last K-tile): zero out contributions where key index $\ge S$.
  • Causal mask: forbid keys $j>i$ — set $S_{ij}$ to a large negative (e.g., $-10^6$) before the exp. In backward, also zero out the same masked positions in $P$ and $\mathrm{d}P$.
  • Recompute $P$ with $L$: $P = \exp(S - L)$. Since $L\ge \max_j S_{ij}$, exponents are $\le e^0$, numerically safe.
  • Accumulation dtype: keep all reductions/matmuls in fp32; cast only on final store.

3.5 Pseudocode (PyTorch-ish math, not a kernel)

# Inputs: Q[K], K[S], V[S], dO[S], L[S]; all [B, S, D] except L [B, S]
dQ = zeros_like(Q); dK = zeros_like(K); dV = zeros_like(V)

for each batch b:
  for each Q-tile rows I (size = bq):
    Qb = Q[b, I, :]           # [bq, D]
    dOb = dO[b, I, :]
    Lb = L[b, I]              # [bq]
    Delta = zeros(bq)         # row scalars

    # ---- Pass 1: dV and Delta ----
    for each K/V-tile cols J (size = bk):
      Kb = K[b, J, :]         # [bk, D]
      Vb = V[b, J, :]         # [bk, D]

      S = (Qb @ Kb.T) * scale               # [bq, bk]
      mask_tail_and_causal_inplace(S, I, J) # set masked to -1e6
      P = exp(S - Lb[:, None])              # [bq, bk]
      dP = dOb @ Vb.T                       # [bq, bk]
      mask_tail_and_causal_inplace(P, I, J); mask_inplace(dP, I, J)

      dV[b, J, :] += P.T @ dOb              # [bk, D]
      Delta += sum(P * dP, dim=1)           # [bq]

    # ---- Pass 2: dQ and dK ----
    dQb = zeros(bq, D)
    for each K/V-tile cols J (size = bk):
      Kb = K[b, J, :]
      Vb = V[b, J, :]

      S  = (Qb @ Kb.T) * scale
      mask_tail_and_causal_inplace(S, I, J)
      P  = exp(S - Lb[:, None])
      dP = dOb @ Vb.T
      mask_tail_and_causal_inplace(P, I, J); mask_inplace(dP, I, J)

      dS = P * (dP - Delta[:, None])        # [bq, bk]
      dQb += dS @ Kb * scale                # [bq, D]
      dK[b, J, :] += dS.T @ Qb * scale      # [bk, D]

    dQ[b, I, :] = dQb

Notes: mask_inplace zeros masked entries; implement causal as j>I (or k_abs > q_abs). In Triton, use the same masking predicates as forward. For dK/dV, if multiple Q-tiles update the same rows $J$, use atomic_add or partition updates.

3.6 What makes it fast

  • No $S\times S$ tensors in backward either. We recompute local $P$ from $L$ and stream $K/V$ twice.
  • Row-scalar $\Delta$ is the only global coupling; it’s cheap to accumulate.
  • Math is exact (no approximation), matching the naïve gradients.

3.7 Minimal checks you should run

  • Compare against a small PyTorch reference (materialize $S$ and $P$ just for testing):

    • Random $B,S,D$ (e.g., $1, 64, 32$), with and without causal.
    • Check $\mathrm{d}Q,\mathrm{d}K,\mathrm{d}V$ with torch.autograd.gradcheck in fp64 (if feasible) or numeric finite differences on tiny problems.

  • Ensure masked positions give zero contributions to all grads.

3.8 Implementation tips (when you Triton-ize it)

  • Use the same grid as forward: programs over (Q-tiles × batch[×heads]).

  • Pass 1 and Pass 2 can be separate kernels (simpler) or fused (harder).

  • Keep tl.dot(..., out_dtype=tl.float32), and mask before reductions.

  • For $\mathrm{d}K,\mathrm{d}V$ collisions, either:

    • assign disjoint $J$ ranges per program, or
    • use tl.atomic_add on the output tiles.

That’s the whole backward story: recompute $P$ with $L$, two streaming passes to get $\mathrm{d}V$ and the row scalars $\Delta$, then $\mathrm{d}Q,\mathrm{d}K$ with one more stream—still no $S^2$ anywhere.
